The decision that changes everything downstream

This one has to be settled before concepting, because it determines whether the experiment surface is a builder or an assembler. Every structural concept branches from here.

Blocking · needs your call

Does the experiment tool own package construction, or does it consume packages owned by the Care packages section, with an in-context route to create one when it is missing?

A. Experiment owns package building

Everything happens inside the experiment. Matches the current prototype. Nothing to learn elsewhere, but the experiment surface has to carry a deep object editor, and the same package gets rebuilt per experiment.

Evidence leans here

B. Experiment assembles library objects

Packages live in Care packages. The experiment attaches them, and a layered work surface lets you author a missing one without losing your place. Matches the existing nav and the "lay all the parts out first" model from the session.

Object model and dependencies

Two relationships in here are doing more work than the current design acknowledges.

Experiment ├─ metadata name, key, hypothesis, environment, tags ├─ test type changes which fields are required ├─ Variants (2..n) │ └─ Packages (1..n) ← platform object │ ├─ Plans (1..n) commitment duration │ │ └─ prices per dosage tier │ └─ Care products ← platform object ├─ Target cohort rule derivable from variants │ └─ extra rule layers device, customer type ├─ Traffic allocation │ ├─ % of eligible traffic entering │ └─ split across variants └─ Publish state environment + active/inactive

Cohort is downstream, not a peer step

Brand, country, vertical and medication are all inferable from the packages attached to the variants. Treating cohort as an independent stage asks for information the system already holds.

Traffic is two-tier, and that is the confusing part

A global eligibility percentage, then a split inside it. 25 percent eligible becomes 12.5 and 12.5. This is the number people get wrong when it is expressed as two unrelated sliders.

Requirements, stated without an interface

What any concept has to satisfy. If a concept cannot do one of these, it fails regardless of how it looks.

R1

Create and edit an experiment without every field being mandatory at creation time.

R2

Set a stable, human-authored identifier, with autogeneration as a convenience.

R3

Assemble variants from reusable packages, and create a missing package without leaving the task.

R4

Duplicate a variant from the variant itself, and understand what the duplicate inherits.

R5

See what differs between variants at any point, not only at review.

R6

Warn on unintentionally identical variants while permitting deliberate A/A.

R7

Derive the cohort rule from configuration, and edit it directly where it is shown.

R8

Express two-tier traffic so a non-specialist can read the resulting audience maths.

R9

Preview the resulting customer-facing surface while configuring it.

R10

Persist work continuously and communicate persistence without a save ritual.

R11

Move between areas of an in-progress experiment non-linearly without losing position.

R12

Publish with environment-specific default states made explicit before the action.

R13

Accommodate future experiment types without re-architecting the primary structure.

R14

Expose the same capabilities to automation as to the interface.

R15

Explain transitional vocabulary in place, at the moment of use.

R16

Give a running experiment a health read, distinct from its setup record.

Edge cases every concept must survive

These are the stress tests. Concepts get scored against them at G1 and G2.

  1. Clone a variant, then change one price in one plan.
  2. Reach variant setup with the needed package not yet existing.
  3. Add a third variant after traffic has already been split.
  4. Two variants end up identical, both accidentally and deliberately.
  5. Return to an earlier area after later areas are complete.
  6. Review a change set where the only difference is buried three levels down.
  7. Run an experiment type that is neither pricing nor packaging, such as a redirect.

Design questions to answer before concepting

Open questions, deliberately not resolved into patterns yet. Your answers steer what gets built at G1.

Q1Is a staged wizard the right spine at all?
The current design assumes linear stages with a completion gate between each. But the object being built is not linear: cohort derives from variants, traffic depends on variant count, and people revisit constantly. An alternative is a single editable experiment object with areas you move between freely, validated at publish rather than at each step. Bears on: D02, D13, R11
Q2What earns the primary work surface?
Right now a read-only flowchart holds two thirds of the screen and the actual work happens in a third. The obvious correction is to flip it. The less obvious question is whether a persistent map is needed at all, or whether orientation can come from something lighter that costs no canvas. Bears on: D02, D11
Q3What is the preview actually for?
Two different jobs are being asked of one panel: showing the customer-facing checkout as prices change, and showing experiment structure and progress. These may want different surfaces, or the structural one may not need to be persistent at all. Bears on: D07, D02
Q4Should difference between variants be a mode, a view, or the default?
Currently difference is a review-time summary and a background tint. It could instead be a persistent comparison view, a toggle available anywhere, or the primary way variants are presented once more than one exists. Bears on: D12, D16, R5
Q5How deep should layered work surfaces go?
Google Tag Manager was named as the model: slide-outs that stack arbitrarily and return you to your place. Package, then plan, then price is already three levels. The question is whether depth is acceptable or whether the model should flatten. Bears on: D11, R3
Q6Does test type branch the flow, or configure a common one?
If choosing a type changes the fields and the setup model, the tool becomes several tools sharing a shell. If type is metadata over a common structure of variants, cohort and traffic, then redirects and page tests slot in without a rebuild. Bears on: D06, R13
Q7What is the dashboard optimising for?
A pulse check on running experiments and a portal into setup records are different products. The evidence is clear that the pulse read is what is missing, but analysis capability is post-MVP, which constrains how far this can go now. Bears on: D01, D17, R16
Q8Is MCP a first-class surface or a later integration?
If automation is genuinely the primary interaction for power users, the underlying model should be designed as an API shape first and the UI as one client. That is an architectural stance with real consequences, not a feature to add later. Bears on: D04, R14
