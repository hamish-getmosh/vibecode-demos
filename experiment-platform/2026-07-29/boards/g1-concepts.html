Four structural models for the experiment flow

Same scenario in all four. Set up a Moshy AU semaglutide pricing test. Variant A is the existing basic package. Variant B is a new premium tier adding a dietitian consult, a longevity consult and a protein shake. The premium package does not exist yet. Target Australia, iOS only, 25 percent of eligible traffic split evenly, publish to staging.

These are structure sketches, not visual design. Grey blocks are deliberate. Each concept had to change both the navigation model and the primary work surface, so none of them is the current design with the panels swapped. That option is included separately as a control so you can see what the extra ambition buys.

Ledger

The experiment is one document, not five gates. Stop asking people to complete stages and let them fill in a record. Orientation comes from a table of contents and a readiness panel, not from locks.

Nav: document plus contents rail Surface: full-width single column Nesting: inline, with focus mode Preview: on demand

You land in an empty record, not step one of five. Everything is present and scrollable from the first second. The contents rail shows what exists; the readiness panel shows what is blocking publish. Nothing is locked.

You start with one column and a plus. Audience sits in a band above the grid, traffic in a band below, because both are small next to variant configuration. There is nothing to complete, only cells to fill.

Spec

If MCP is genuinely the primary interface for power users, design the object first and treat the UI as one client of it. The experiment is a readable structured record; forms are just one way to edit it, and an agent is another.

Nav: command bar plus two views Surface: editable structured spec Nesting: expand in place Preview: rendered view

You can type or you can click. The command bar accepts the same operations MCP does, and the spec below is the live object. Nothing is hidden behind a form you cannot see the shape of.

Where I have landed, provisionally

Two of these are probably one concept

B Bench and C Assembly are solving adjacent halves of the same problem. Bench makes difference structural but has no good answer for where packages come from. Assembly answers exactly that, but its variant comparison is coarse, only at the part level. A hybrid where the workspace is a comparison grid and the cells are filled from a parts library covers more of the requirements than either alone.

A Ledger is the safest genuine improvement. It removes the gating problem and the review-destination problem without asking anyone to learn a new mental model. If the appetite for change is moderate, this is the one.

D Spec is the most interesting and the most dangerous. It is right about where the tooling is going and wrong about who else has to use it. My read is that its best ideas, explicit inheritance, native diff, addressable paths, should be absorbed into whichever concept wins rather than shipped as the primary interface.

Kill anything?If a concept is a dead end, say so now and I will not carry it into mid-fi.
Hybridise B and C?My instinct. Comparison grid as the workspace, library parts as the fill.
Settle the scope callDoes the experiment own package building, or consume from the library? Everything downstream depends on it.
