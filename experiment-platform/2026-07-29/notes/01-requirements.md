# Requirements inventory

Source evidence: Figma design file `pS2pi2BR6d9xpE4hxvUWmA` (Dev Mode) and the Hamish / Alice research session, 28 Jul 2026.

This file separates three things that are easy to conflate: what the system must do, what the current design does, and what was proposed in the room. Nothing in the current structure is assumed to survive.

## A. What the platform already is

Observed from the dashboard frame (`222:19933`), left navigation:

| Section | Status |
|---|---|
| Experiments | built in prototype |
| Customer properties | exists in nav |
| Care packages | exists in nav |

**Structural finding.** Care packages and care products already have dedicated homes in the platform. The current experiment flow nonetheless contains a full package builder inside a narrow sidebar. The platform has an object library and the experiment flow ignores it. This is the single biggest architectural tension in the current design.

## B. Object model and dependencies

```
Experiment
  ├─ metadata (name, key, hypothesis, environment, tags)
  ├─ test type (pricing/packaging | page flow | copy) → changes required fields
  ├─ Variants (2..n)
  │    └─ Packages (1..n)          ← reusable platform object
  │         ├─ Plans (1..n)        ← commitment duration, e.g. 3-month vs month-to-month
  │         │    └─ Prices per dosage tier
  │         └─ Care products (0..n) ← reusable platform object
  ├─ Target cohort rule            ← partly derivable from variant attributes
  │    └─ additional rule layers (device, customer type, etc.)
  ├─ Traffic allocation
  │    ├─ % of eligible traffic entering the experiment
  │    └─ split across variants
  └─ Publish state (environment + active/inactive)
```

Two derived relationships matter for design:

1. The cohort rule is **downstream** of variant configuration. Brand, country, vertical and medication can be inferred from the packages attached.
2. Traffic is **two-tier**. A global eligibility percentage, then a split within it. This is the part that confuses non-specialists.

## C. Current flow

Five stages: Overview → Variant setup → Target cohort → Traffic split → Publish.

Layout across every stage: roughly two thirds of the screen is a read-only flowchart canvas of summary cards, one third is a right-hand configurator sidebar containing the stepper, the form and the primary action.

## D. Evidence

Each item cites the transcript timestamp. Problems are separated from the solutions proposed in the room, because a proposed solution is not a requirement.

### D1. Dashboard is a setup artifact, not a pulse check
- Interface reads as information-dense on first landing (00:09:11).
- Traffic split percentages occupy card space but are "nice to know", not critical (00:12:30).
- What is actually wanted at a glance: what is live, traffic volume per week, brand recognition via logos rather than reading text pills, and some read on the primary metric with a confidence interval and a projection of when significance will be reached (00:12:30, 00:13:38, 00:14:39).
- Staging versus production does not warrant much visual weight, since most experiments end up in production (00:13:38).
- Stated principle: once setup is done, setup information stops being interesting. The dashboard should serve a "pulse check lens", not a "setup or utility lens" (00:14:39, 00:16:43).

### D2. Hierarchy is inverted
- The configurator is where the work happens, but it presents as a sidebar while the passive canvas occupies the main area (00:36:52).
- Requested: primary work surface at roughly two thirds, preview at one third, plus an option to expand the configurator to full screen (00:36:52, 00:37:52).
- Excessive scrolling in the narrow panel. With more width, plans could sit side by side and be compared at once (00:37:52).
- Left-to-right reading order argues for controls on the left (00:18:49).

### D3. Mandatory fields get defeated
- Hypothesis is required, but the real record lives in a Notion database, so a required field just produces junk input (00:18:49, 00:19:57).

### D4. The UI is not the only intended interface
- Current working method is Cursor plus MCP: settle the hypothesis in chat, write the Notion record, drive GrowthBook, generate Amplitude dashboards (00:19:57, 00:21:19).
- Full MCP control over this tool is described as a game changer, with the UI acting as an edit and review layer rather than the sole entry point (00:22:18, 00:23:21).
- A UI is still required and must stand alone for people who do not use MCP (00:23:21).

### D5. Experiment key is an identifier, not a description
- Autogenerated semantic keys become "description slop" and vary by author (00:25:18).
- An ID-based convention (004) is searchable in Amplitude and stable across tools (00:25:18).
- Keys cannot be changed once an experiment is live (00:24:18).
- Agreed compromise: autogenerate with manual override on the key, enforce a naming convention on the experiment name instead (00:26:16, 00:27:37).

### D6. Test-type gating risks boxing the tool in
- Three options presented: pricing and package, page flow and structure, copy and content. A pure redirect test does not fit any of them (00:28:33).
- Test type changes both the form fields and the setup model, and a future drag-and-drop page editor is the stated reason for the canvas direction (00:29:43, 00:30:44).
- MVP is scoped to pricing and packaging, but the structure should not foreclose other types (00:31:49).

### D7. No live preview of the thing being configured
- Requested: a mobile checkout render that updates as prices and plans change during configuration (00:32:48).

### D8. Terminology is in transition
- Package, care product and plan are not self-evident. "Plan" currently denotes commitment duration, which is not obvious (00:33:53, 00:45:09).
- Tooltips wanted throughout; one tooltip in the prototype was already broken (00:34:52, 00:35:57).
- The stakes make hesitation costly: a configuration error is expensive, so the design should reduce second-guessing (00:34:52).

### D9. Variant duplication is inverted
- Expected model: stand in variant A and clone it. Actual model: create a distinct variant B, then choose "copy from variant A" (00:39:54, 00:40:50).
- The copy option should be surfaced in both places, as a shortcut (00:41:47).
- Copy-from-variant-A currently reads as attached to package one rather than to the variant as a whole (00:43:46).

### D10. No guard against accidental A/A
- A warning is wanted when variants are identical, while still permitting deliberate A/A tests for noise measurement (00:41:47, 00:42:39).

### D11. Package building does not belong in the sidebar
- Configuring plans and packages inside the experiment is too much for the space and involves heavy scrolling (00:46:17).
- Preferred model, stated as an IKEA metaphor: lay out all the parts first, then follow the instructions. Build the packages, then assemble them into variants (00:47:23, 00:51:33).
- The experiment tool should concentrate on assigning building blocks to variants, cohorts and traffic splits (00:50:21).
- Critically, users must still be able to create a missing package mid-flow without navigating away (00:51:33, 00:52:27).
- Reference model named explicitly: Google Tag Manager's dedicated layered work surfaces that slide out, stack to arbitrary depth, and return you to your place (00:48:32, 00:49:35).

### D12. Change indication is at the wrong granularity
- A tinted background across the whole window forces cross-comparison to find what actually changed (00:55:22, 00:56:27).
- Wanted: field-level markers, a small dot, with a package-level marker when an entire package is new (00:56:27, 00:57:22).
- Package headers carry too much contrast and pull attention; a see-through fill is preferred (00:57:22).

### D13. Save semantics create anxiety
- "Save and continue" implies that navigating back without clicking will lose work (00:58:19).
- The button exists only for reassurance; data persists regardless (00:58:19).
- Preferred wording: "Complete" or "Next", with save language removed so persistence is assumed (00:58:19, 00:59:28).
- Adding a third variant currently requires navigating back a step (00:59:28).

### D14. Cohort rules do not look editable
- The derived default rule is presented as static grey text (01:00:29, 01:01:33).
- Deriving the rule from variant setup is valued, since it removes re-entry friction (01:00:29).
- Wanted: common properties (country, brand, vertical, customer type) surfaced as selectable bubbles or radio toggles rather than dropdowns, with long-tail properties remaining in dropdowns given there may be forty or more (01:01:33, 01:02:24, 01:03:37).
- Rule layers can be added, for example device type is iOS (01:00:29).

### D15. Two-tier traffic maths is not legible
- The two tiers of splitting catch people out, particularly when explaining to the marketing team (01:04:42).
- Wanted: a visual, bar chart or funnel, showing 25 percent eligible then 12.5 and 12.5 within it (01:04:42, 01:05:31).

### D16. Review does not answer the reviewer's question
- The review page cannot be edited directly; changes require navigating back (01:05:31).
- Wanted: the exact differences between variants stated plainly, for example variant B is identical to variant A except for one new package (01:06:34).
- Publish behaviour differs by environment: staging is active on publish, production is inactive on publish and needs a manual toggle (01:05:31).

### D17. Analysis lives elsewhere, for now
- A button creates an Amplitude dashboard on publish (00:15:37).
- Wanted: export a JSON schema of everything needed so Amplitude AI can build the dashboards without manual setup (00:16:43, 00:17:45).
- An initial layer of results inside the experiment record is desirable but acknowledged as post-MVP (00:16:43).

## E. Requirements, stated without a UI

Capability statements derived from the evidence. These are what any concept must satisfy.

**R1.** Create and edit an experiment without every field being mandatory at creation time.
**R2.** Set a stable, human-authored identifier, with autogeneration available as a convenience.
**R3.** Assemble variants from reusable packages, and create a missing package without leaving the task.
**R4.** Duplicate a variant from the variant itself, and understand what a duplicate inherits.
**R5.** See what differs between variants at any point, not only at review.
**R6.** Detect and warn on unintentionally identical variants while permitting deliberate A/A.
**R7.** Derive the cohort rule from configuration, and edit it directly where it is displayed.
**R8.** Express two-tier traffic allocation so a non-specialist can read the resulting audience maths.
**R9.** Preview the resulting customer-facing surface while configuring it.
**R10.** Persist work continuously and communicate that persistence without a save ritual.
**R11.** Navigate between areas of an in-progress experiment non-linearly, without losing position.
**R12.** Publish with environment-specific default states made explicit before the action.
**R13.** Accommodate future experiment types without re-architecting the primary structure.
**R14.** Expose the same capabilities to automation (MCP/API) as to the interface.
**R15.** Explain transitional vocabulary in place, at the moment of use.
**R16.** Give a running experiment a health read, distinct from its setup record.

## F. Edge cases any concept must survive

1. Cloning a variant, then changing one price in one plan.
2. Reaching variant setup with the needed package not yet existing.
3. Adding a third variant after traffic has already been split.
4. Two variants ending up identical, both accidentally and deliberately.
5. Returning to an earlier area after later areas are complete.
6. Reviewing a change set where the only difference is buried three levels down.
7. An experiment type that is neither pricing nor packaging, such as a redirect.

## G. Open scope question for R0

The evidence points to a boundary decision that changes everything downstream:

> Does the experiment tool **own** package construction, or does it **consume** packages owned by the Care packages section, with an in-context path to create one?

The nav structure and the IKEA metaphor both point to the second option. This is the question to settle before concepting, because it determines whether the experiment flow is a builder or an assembler.
